1       Purpose and relationship to the main text

The main paper argues that comparable reflectance has to be constructed and that researchers should
be able to examine how that construction was made. This supplement provides the detail needed to
assess that claim: processing contracts and transformations, the intended drone artifact sequence,
the first 43-flight production attempt, the streaming bulk workflow inspected in September 2026,
historical QA records, and the supplied 122-flightline analysis. Development history, neighboring-
software comparisons, and the prospective QA and resource protocol are included here so that the
main paper can stay focused on the scientific problem.
The organization follows the questions a reader is likely to ask. What is the software intended to
produce? Which numerical transformations does it apply? How are completion and QA judged?
What happened in controlled tests and real-data runs? Which conclusions can be drawn from the
collection analysis, and what remains to be tested? Detailed provenance and future protocols follow
the results they qualify.

Four terms keep the claims consistent. Implemented means that behavior is present in source code.
Tested means that a controlled fixture exercises a defined contract. Demonstrated refers to artifacts
and behavior recorded in a real-data run. Scientifically validated requires independent observations
or a justified external reference. Thus, the drone campaign demonstrates discovery, staging, and
persistence of intermediate products, but not completion of the full drone route.


2    Software scope and supported paths

SpectralBridge has two observation-level paths and one collection-level path. NEON processing
produces source-product and geometry-normalized hyperspectral representations, configured target-
band products, analysis tables, and QA. Drone processing ingests supported local observations while
preserving their identity, correction availability, and provenance (Earth Lab, 2026am; Earth Lab,
2026m). The bulk path then catalogs eligible target products and reads aligned ENVI windows;
merged Parquet remains available for compatibility. Bulk analysis starts from completed products
and does not rerun geometry normalization or target-band weighting (Earth Lab, 2026a).
The project-level relationship Drone → NEON → Landsat is conceptual. NEON supplies a dense
reference spectrum from which configured MicaSense- and Landsat-like band representations can be
constructed. The package does not implement a direct, universal drone-to-Landsat conversion, and
target-band weighting does not alter spatial support (National Ecological Observatory Network,
2026; Earth Lab, 2026am; Earth Lab, 2026s).
Each observing system brings a different strength. Imaging spectroscopy preserves contiguous
spectral information (Goetz et al., 1985); the NEON Airborne Observation Platform applies it
to repeatable ecological observation (Kampe et al., 2010); Landsat provides a long calibrated
record at moderate resolution (Wulder et al., 2022); and compact UAV instruments provide flexible,
very-high-resolution sampling while demanding careful measurement design and calibration (Aasen
et al., 2018; Mamaghani and Salvaggio, 2019). SpectralBridge addresses the spectral and workflow
parts of relating these systems, not the entire comparison problem.

3.2     Optional across-track half-flight processing

Full-flightline processing remains the default. When split across track=True, SpectralBridge
downloads or reuses one source HDF5 file, divides the across-track columns into left and right
windows, and writes each window to a separately suffixed product tree. If the sample count is odd,
the right window receives the additional column. The two windows share source identity but are
independent pipeline units for output paths, QA, and restart (Earth Lab, 2026o; Earth Lab, 2026i).
This mode changes more than memory layout. Topographic and BRDF estimation for each run sees
only the pixels in that window, so half-flight products are not assumed to be numerically identical
to the corresponding subset of a full-flightline result. Bulk-run records must therefore distinguish

full, left-half, and right-half processing. The mode provides an operational option for large inputs,
but its effect on peak memory, run time, correction estimates, and seam behavior must be measured
rather than inferred (Earth Lab, 2026o; Earth Lab, 2026ao).


4     Scientific transformations

4.1   Configured target-band weighting

Nominally similar bands can have different relative spectral responses and therefore produce different
reflectance values over the same target (Chander et al., 2013; Roy et al., 2016; Claverie, 2023).
SpectralBridge addresses this spectral part of the comparison by applying sampled target-band
weights to the NEON spectrum. The result is a configured target-band representation of the NEON
observation, not an independently observed target-sensor measurement. Some source code and
historical QA records call this stage spectral convolution; the manuscript uses target-band weighting
when discussing its scientific meaning.
For reflectance samples ρi and response weights sb,i already sampled on the same source-band grid,
the implemented target-band quantity is

The implementation normalizes each response by its discrete sum and applies a floating-point matrix
product (Earth Lab, 2026aa). The wavelength vector is checked for dimensional alignment but
is not used for wavelength-interval quadrature. The routine therefore assumes that the supplied
sampled weights already encode the intended wavelength sampling and does not independently
establish their units, ordering, spacing, provenance, or spectral overlap.
Configured outputs include representations labeled for Landsat 5 TM, Landsat 7 ETM+, Landsat 8
OLI, Landsat 9 OLI-2, and MicaSense, together with downstream affine coefficient sets for selected
MicaSense-like and Landsat-like variables. Packaged center and full-width-at-half-maximum values
are stored in the repository’s sensor-parameter JSON (Earth Lab, 2026q). These parameters can
define Gaussian approximations but are not themselves measured relative spectral response curves;
the Landsat 8 Operational Land Imager, for example, has measured bandwise relative spectral
responses that determine its actual wavelength weighting (Barsi et al., 2014). More generally,
quantitative UAV multispectral use depends on documented geometric and radiometric calibration,
and camera-specific characterization can reveal departures from factory assumptions (Aasen et al.,
2018; Mamaghani and Salvaggio, 2019; Cao et al., 2019).
Some configured Landsat-like products receive an empirical percentage adjustment after Equation 1.
The inspected coefficient files describe adjustments derived from Table Mountain HLS median
differences and warn that their band indices are wavelength-aligned rather than interchangeable
with native sensor numbering (Earth Lab, 2026r). Product headers and QA artifacts record
whether the adjustment was applied, but the purely weighted representation is not always retained
as a separate canonical raster. Target-band weighting and brightness adjustment are therefore
distinct measurement states even where the artifact chain combines them, and transferability of
the adjustment beyond its derivation context has not been established. Evaluations of bandpass-
adjustment techniques show that simple linear, spectral-library, adaptive, and nonlinear methods

have different data requirements and performance; no one fitted form is a complete definition of sensor
harmonization (Claverie, 2023). HLS version 2.0 further demonstrates that operational harmonization
combines atmospheric correction, cloud and shadow handling, directional normalization, bandpass
adjustment, and common gridding (Ju et al., 2025).
Five controlled source/target band-count variations agreed with an independently implemented
normalized-weight calculation to an absolute tolerance of 2 × 10−7 (Earth Lab, 2026ar). This
tests the arithmetic contract. It does not validate weight provenance, usable spectral support, or
agreement with measured satellite observations.
Declared poor-quality source bands are retained visibly in the R10C evidence, but the archived
reports do not establish whether they received nonzero weight in each target band (Earth Lab,
2026w; Earth Lab, 2026y). Before scientific interpretation, the planned study must report usable
source-wavelength coverage for every target-band representation, identify overlap with declared
poor-quality bands, and define the status assigned when usable support falls below the recorded
thresholds. Until then, an arithmetic pass for spectral weighting should not be read as evidence
that every target band has adequate scientific support.


4.2   Topographic and BRDF normalization

SpectralBridge applies sun-canopy-sensor plus C (SCS+C) topographic normalization followed
by kernel-driven bidirectional reflectance distribution function (BRDF) normalization. SCS+C
is attributed to its forest topographic-correction source (Soenen et al., 2005); RossThick and
LiDenseR belong to volume- and geometric-scattering model lineages developed and operationalized
across several studies (Ross, 1981; Roujean et al., 1992; Li and Strahler, 1992; Wanner et al.,
1995; Schaaf et al., 2002). The source implementation has a separate provenance: calc cosine i,
calc volume kernel, and calc geom kernel, together with portions of the surrounding correction
module, explicitly identify adaptation from the GPLv3-licensed HyTools project (Chlus et al., 2025;
Earth Lab, 2026z). In the default mode, one SCS+C term per band is estimated from pixels passing
the source no-data and finite-value masks, using streamed sufficient statistics across the flightline.
Correction is applied in full-width row strips. Scene-level BRDF coefficients are then applied using
those kernels, scene-mean solar zenith, local view geometry, and a conventional normalization target
of 45-degree solar zenith, nadir view, and zero relative azimuth; this is not the actual acquisition
geometry of Landsat or NEON (Queally et al., 2022; Earth Lab, 2026ao). Non-finite or unsuitable
correction ratios are replaced by neutral factors rather than allowed to create extreme values (Earth
Lab, 2026z). The fraction of pixels and bands receiving neutral fallbacks should be retained as a
QA diagnostic because numerical stability does not imply that a correction was applied.
An optional tiled mode fits independent topographic terms in non-overlapping 100 × 100-pixel
tiles. This reduces fitting scope but creates a specific QA question: whether grid-aligned seams
appear in the normalized product. The canonical normalized cube combines topographic and BRDF
operations. Separate topographic-only and BRDF-only cubes are not retained, so attribution of
their individual effects requires additional runs or outputs (Earth Lab, 2026ao; Earth Lab, 2026s).
These empirical and semi-empirical models alter observed relationships with terrain and acquisition
geometry. Independent reference observations are needed to determine whether the resulting
reflectance is more accurate for a particular scientific use, especially when vegetation composition
covaries with slope or aspect (Soenen et al., 2005; Queally et al., 2022).

4.3   Spatial support

Spectral weighting changes band space, not pixel footprint. A target-band representation of a NEON
pixel and an actual Landsat footprint remain different mixtures even when they use similar band
labels; a sensor’s point-spread function can also extend the contributing area beyond a nominal
pixel boundary (Teillet et al., 1997; Woodcock and Strahler, 1987; Huang et al., 2002). Spatial
comparison must distinguish grain, support, extent, and the scale of the ecological process (Dungan
et al., 2002). SpectralBridge retains geospatial rasters and polygon-extraction products so users
can define co-registration and aggregation explicitly (Earth Lab, 2026s; Earth Lab, 2026m). The
aggregation rule determines which fine-resolution observations contribute, how incomplete overlap
is handled, and whether the resulting quantity represents area, cover, or another ecological target.


5     Drone processing pipeline

The drone pipeline is intended to prepare the independently acquired fine-resolution side of the
comparison. It recursively discovers local HDF5 inputs and supports configured local TIFF inputs,
preserves provenance from original filenames, and stages a working HDF5 representation. The
intended downstream sequence is working HDF5, native-drone ENVI representation, geometry
normalization where supported, geometry-normalized native-drone representation, optional applica-
tion of reviewed affine relationships to construct configured Landsat-like variables, full-image or
polygon extraction, Parquet, and QA (Earth Lab, 2026m; Earth Lab, 2026aj). This use case follows
a broader ecological need to connect reproducible UAS observations with NEON’s continental
sampling framework (Koontz et al., 2022).
Topographic and BRDF normalization require the corresponding terrain, view, and solar geometry.
Radiometric panel methods, empirical-line calibration, camera characterization, and downwelling-
sensor geometry can each influence retrieved UAV reflectance and must be recorded as part of the
measurement definition (Wang and Myint, 2015; Cao et al., 2019; Schneider-Zapp et al., 2019; Origo
et al., 2025). The intended QA record distinguishes a correction that ran from one that was skipped
because geometry was unavailable or that used a fallback after a quality check. Users can request
all available pixels or restrict extraction to intersecting polygons. Each discovered flight receives a
separate output directory with drone-native identity. Which artifacts are required depends on the
resolved configuration; completion must therefore be evaluated against that configuration rather
than against a universal list or process return code.
The optional affine relationships require especially careful language.       The documented post-
normalization equation is

where M is a corrected native-drone variable and L is a configured Landsat-like variable. The
release-candidate documentation specifies wavelength-aware source-to-target mapping, a versioned
reviewed coefficient registry, and a fixed production policy using the site-balanced relationship.
The drone route neither estimates these coefficients at runtime nor performs spectral convolution;
convolution remains part of the NEON hyperspectral path. If an approved production registry is

Optional external QA can search for an overlapping Landsat Collection 2 Level 2 scene, use a

6     File contracts, provenance, and restart behavior

The phrase “outputs are the API” means that stages communicate through named files, not only
through values held in memory (Earth Lab, 2026p). Those files preserve the scientific sequence:
source observation, working or source-product representation, geometry/model summary, geometry-
normalized representation, configured target-band representation, extracted table, and QA record.
The resolved configuration determines which of them are required. This design is consistent with
FAIR workflow and research-object practices that package data, software, parameters, provenance,
and results as one inspectable record (Goble et al., 2020; Soiland-Reyes et al., 2022).
This design helps localize a problem, although it does not diagnose the cause automatically. A
source-product cube can show whether an unexpected pattern was already present; the geometry-
normalized cube can show whether it appeared during normalization; the target-band product can
reveal a change during band construction; and the Parquet output can reveal a change during
extraction or merging. Some boundaries remain coarse: topographic and BRDF effects share one
cube, and weighting and brightness adjustment can share one target-product stage. The files can
therefore identify the stage at which a pattern appeared without always isolating the operation
within that stage (Earth Lab, 2026p; Earth Lab, 2026i; Earth Lab, 2026s).
On rerun, a stage can reuse artifacts that pass its format checks and reconstruct outputs that are
absent or rejected (Earth Lab, 2026f; Earth Lab, 2026aq). JSON must parse, ENVI image/header
pairs must pass internal readability checks, and Parquet outputs receive schema-read checks. QA
reuse is stricter: the public contract requires matching schema, parameters, thresholds, software
version, and input/output fingerprints (Earth Lab, 2026af). Format checks, QA reuse, and completion
are therefore separate decisions. Reproducible reuse requires retaining or recording:

    • the full software commit and installed package versions;
    • the command and resolved configuration;
    • source identifiers and, where possible, checksums;
    • packaged response-definition versions or exact response arrays;
    • the expected artifacts implied by the resolved configuration and their stage dependencies;
    • produced artifacts and their checksums; and
    • the execution environment and resource configuration.

Two important gaps remain: the scene-wide SCS+C coefficients applied to the geometry-normalized
cube and the exact per-output-band weights are not fully serialized in the canonical record (Earth
Lab, 2026ao; Earth Lab, 2026aa; Earth Lab, 2026s). Both are needed to reconstruct every numerical
transformation exactly.

Pixels are nested within flightlines, and flightlines are nested within sites. Pooled pixel regressions
are therefore descriptive and must not present pixel count as the number of independent land-
scapes (Hurlbert, 1984). The three reported estimands differ only in group contribution: pixel-pooled
fitting gives each selected pixel equal weight, flightline-balanced fitting gives each flightline equal
total weight, and site-balanced fitting gives each site equal total weight. The exported weighting
descriptions and replicate counts were checked against these definitions. The balanced summaries
are sensitivity analyses, not independent replications or a hierarchical uncertainty model. Validation
of spatially and hierarchically structured data should preserve that dependence in its training and
test partitions (Roberts et al., 2017). Leave-one-site-out evaluation fits on two observed sites and
evaluates the third; with only three sites, its three folds describe those particular site/acquisition
combinations rather than a population of possible sites or a general model area of applicability (Meyer
and Pebesma, 2021). All summaries inherit the limitations of the underlying products: paired
synthetic bands share one corrected NEON source and do not constitute independently acquired
drone or Landsat observations (Earth Lab, 2026b; Earth Lab, 2026d).
For each chunk, counts, means, centered sums of squares, and cross-products are accumulated in
numerically stable bivariate moments. Merging produces flightline and collection records; inverse
merging removes a held-out site’s contribution to training. A second bounded pass calculates errors
that are not all recoverable from moments alone (Earth Lab, 2026an; Earth Lab, 2026c). The bulk
manifest and per-flightline checkpoint records should accompany source hashes and the resolved
configuration; restartability is not a substitute for exact-run provenance.
The direct reader checks dimensions, transform, and coordinate reference system and applies sensor-
wide finite/no-data rules together with the configured minimum-value threshold. It reads stored
raster values without itself establishing their physical scale (Earth Lab, 2026an). Concurrency,
window size, and storage throughput therefore matter both to reproducibility and to the cost

--- Source page 11 ---
of repeated reads. Explicit dataset materialization and the compatibility input path should be
benchmarked separately, not described as mandatory costs of streaming.
The results interpretation layer operates on the manifest and compact model/group tables without
reopening the source rasters (Earth Lab, 2026g). This manuscript’s focused examination similarly
uses the supplied CSV exports. Neither workflow supplies a complete upstream QA census merely
by accepting inputs into a relationship analysis.


7.1    Additional spectral-library reporting route

The release-candidate interface also exposes spectral-library preflight and reporting as first-class
routes. A preflight inspects a supplied Parquet library’s schema, group counts, and anticipated
rendering work before analysis. The reporting route reads that library in place and can produce
species summaries, quantiles, spectral ensembles, hierarchical variability summaries, traceable
extreme-spectrum diagnostics, and optional multipage reports without making a second row-level
copy of the library (Earth Lab, 2026aj). This route is relevant to the package’s broader analysis
design and is included in the documented exact-artifact smoke. No executed spectral-library
output was supplied with the manuscript evidence bundle, however, so this manuscript treats it as
implemented and bounded-test functionality rather than a demonstrated scientific result.


8     Quality-assurance model

Every run raises four questions. Did the code execute? Were the products required by the
resolved configuration written and readable? What did QA report about those products? Do
independent observations support their scientific interpretation? We call these process, artifact,
QA, and validation status. Remote-sensing frameworks likewise treat validation as evidence
assembled from representative comparisons and characterized reference measurements, not as
a single binary label (Morisette et al., 2006; Origo et al., 2020). The 43-flight campaign is a
concrete example: it reached intermediate and QA states but did not satisfy its downstream artifact
contract (SpectralBridge project team, 2026).
SpectralBridge separately uses pass, warn, and fail within evaluated QA records. Table 4 defines
that narrower vocabulary (Earth Lab, 2026s; Earth Lab, 2026w).

    Status            Meaning
    pass              The evaluated artifact or numerical quantity met its configured rule.
    warn              The evaluated quantity or known condition requires interpretation; the
                      status does not independently establish full pipeline completion.
    fail              A required artifact or evaluated rule prevents the intended interpretation.
    Not evaluated     Available artifacts do not answer the stated question; absence of evidence
                      is not converted into a pass.

QA artifacts include visual panels, machine-readable JSON and metric records, stage-level HTML
and JSON reports, and an optional combined PDF (Earth Lab, 2026s). These products record
observed values, thresholds, provenance fields, and reasons that a diagnostic could not be evaluated.
Several recorded thresholds are provisional workflow diagnostics rather than externally validated
scientific decision limits.
For a collection QA census, the emitted combined status is treated as authoritative rather than
reconstructed from selected metrics. pass, warn, and fail counts are mutually exclusive. A
missing or unreadable report remains a separate category in the attempted-flightline denominator.

8.1   Validation tiers and installed-artifact checks

The inspected documentation separates validation into two tiers. Tier A builds the wheel and
source distribution, installs the exact artifact into a clean environment outside the source checkout,
blocks network access, and runs small deterministic smoke fixtures through the NEON, drone, and
bulk entry points. This bounded strategy addresses a common scientific-software problem: many
computations lack a complete test oracle even when their software contracts can be tested (Kanewala
and Bieman, 2014). The public validation page reports a separate offline campaign with 40 of 40
passing variations: five variations for each of eight modules. It records revision bebf707, marks the
working tree as dirty, and gives 14 August 2026 as its last update. This supports the recorded module
checks but does not uniquely identify a clean source state (Earth Lab, 2026al). The 4 September
audit reports successful clean wheel checks on local Python 3.10, 3.11, 3.12, and 3.14 interpreters and
a source-distribution check on Python 3.10. The tag-release workflow has the narrower supported
gate of the exact wheel on Linux with Python 3.10–3.12 and the source distribution on Python
3.10 (Earth Lab, 2026ap; Earth Lab, 2026v; Earth Lab, 2026k).
The NEON smoke fixture uses an 8 × 8 × 32 synthetic cube and exercises geometry normalization,
configured target products, Parquet conversion and merging, QA, and restart. Drone smoke tests
exercise full-image and polygon routes, and bulk smoke tests exercise census, relationship fitting,
coefficient export, leave-one-site-out evaluation, optional materialization, and restart. The release-
candidate README also identifies spectral-library reporting as part of the bounded exact-artifact
smoke (Earth Lab, 2026aj). These tests provide evidence for packaging, stage connectivity, artifact
readability, and bounded restart behavior. They do not test production scale or scientific accuracy.

15     Reproducibility checklist

The checklist below turns those boundaries into a practical archive specification. For every included
flightline, record the following items, consistent with guidance for reproducible computational
research, FAIR workflows, and packaged research objects (Sandve et al., 2013; Wilson et al., 2017;
Goble et al., 2020; Soiland-Reyes et al., 2022):

  1. the full input identifier, product code, site, date, input checksum, and any embedded identity
     metadata used to verify the filename-derived identity;
  2. source file size in bytes;
  3. the complete command and resolved configuration, including full- or half-flight mode and
     window;
  4. the required artifact contract implied by that configuration and the completion rule applied
     to it;
  5. the SpectralBridge commit, exact wheel or source-distribution checksum, and dependency
     environment;
  6. worker count, host information, wall time, and peak resident memory;
  7. hashes for source-product, corrected, convolved, tabular, and QA outputs;
  8. stage-level and combined QA JSON records;
  9. the exact spectral-response definitions and brightness coefficients used;
 10. for drone affine products, the reviewed registry version and checksum, estimator identity,
     wavelength mapping, coefficient identifiers and values, confidence state, and strictness policy;
 11. for optional external Landsat QA, the product identifier, acquisition time, masks, query or
     cache record, common grid, resampling, overlap rule, and temporal offset;
 12. any manual exclusions, reruns, or interpretation decisions;
 13. both the original and corrected run records when a completion-accounting defect is discovered,
     including which intermediate artifacts were reused;
 14. links between every reported study statistic and the contributing source-flightline records; and
 15. the bulk run identifier, manifest, source catalog, duplicate decisions, weighting scheme, stored-
     value scaling, reference-value definition, and streaming, compatibility, or materialization mode
     when bulk analysis is used.

The R10C artifact records its generating commit and bounded input fingerprint, but it does not
package the command, resolved configuration, dependency environment, full input checksum, and
report checksum as one replay record. A publication archive should close that gap and should either
rerun R10C under the publication commit or retain the revision difference explicitly (Earth Lab,
2026w; Earth Lab, 2026y). The drone archive has the complementary gap: it preserves intermediate
campaign output but does not identify the production revision or demonstrate fulfillment of the
requested downstream contract (SpectralBridge project team, 2026).

A     Software lineage and implementation provenance

SpectralBridge began as an effort to use HyTools directly for NEON HDF5 and ENVI input/output,
image and chunk iteration, topographic and BRDF correction, spectral resampling, and output
writing (Chlus et al., 2025; Earth Lab, 2025a). As sensor-specific, operational, and evidential
requirements accumulated, the team repeatedly modified, specialized, and replaced parts of that
pathway. The current package is therefore not a thin interface around HyTools. HyTools nevertheless
remains its closest implementation predecessor and an important part of its scholarly provenance.
The relationship is not captured by a single label. It includes published scientific methods im-
plemented by both projects, source explicitly adapted from HyTools, historical HyTools source
retained outside the active package tree, interoperability work during the transition, and workflow
components for which the reviewed evidence identifies no material HyTools implementation lineage.
Because the available audit does not quantify line-by-line derivation across the complete codebase,
the manuscript does not convert the team’s qualitative experience of an extensive rewrite into a
percentage-of-code claim.
These categories answer different questions. A scientific citation identifies the origin and interpre-
tation of a method. A source notice identifies implementation lineage. A dependency declaration
states what must be installed at runtime. A historical repository tree records development history.
None substitutes for the others. In particular, implementing the same published equation does not
by itself establish code adaptation, while removing HyTools from runtime dependencies does not
remove adaptation already present in source.

A.4     SpectralBridge contribution boundary

The package’s contribution does not depend on presenting established correction equations or
adapted low-level components as newly invented. The evidence supports a contribution at the
level of organization and application: explicit sensor and product handling; named intermediate
artifacts; target-band construction and recorded translation states; drone preparation and extraction;
restart and completion contracts; QA and provenance records; and campaign- and collection-scale
analysis (Earth Lab, 2026p; Earth Lab, 2026i; Earth Lab, 2026m; Earth Lab, 2026s; Earth
Lab, 2026b). These components combine established environmental remote-sensing methods and
attributed prior software into an inspectable system built for a specific cross-sensor measurement
problem.

--- Source page 34 ---
This distinction reinforces the manuscript’s broader evidential argument. Inspectable scientific
software should expose not only input provenance, parameters, transformations, QA, and outputs,
but also the lineage of important implementations used to perform those transformations. A reader
can then distinguish the origin of a scientific method, the ancestry of its code, the package required
at runtime, and the workflow contribution made by SpectralBridge without collapsing them into a
single novelty claim.

C     Prospective QA and resource protocol

An earlier study plan specified 100 NEON flightlines. We retain it as a prospective protocol rather
than applying it retroactively to either the 122 accepted flightlines in the bulk collection or the
separate 43-package drone attempt. Before NEON collections are combined, the selection rule,
attempted-input list, configurations, and missing QA and resource records must be reconciled. These
runs answer different questions and should remain separate records.
The study treats each original source flightline as one operational unit for completion, QA prevalence,
and resource reporting. Pixels are not pooled across flightlines for the primary summaries, because
cube dimensions differ and pooled pixels would allow larger flightlines to dominate. Left and right
processing halves, where used, remain paired partitions of one source flightline and are not counted
as independent flightlines. Site is the highest unit for statements about out-of-site operational or
diagnostic stability (Hurlbert, 1984).
The study record should define the sampling frame and selection rule; represented sites and years;
attempted, completed, excluded, and repeated flightlines; processing partitions; publication commit
and resolved configuration; execution environment; and missing or unreadable QA reports. Missing

reports remain in the denominator. Runs combined in one summary must use the same response
and brightness definitions, QA schema, and thresholds. If a run is replaced, the original attempt
and the reason for replacement should remain in the archive.
Completion and status outcomes will be reported as counts and percentages; continuous diagnostics
will be summarized by median, interquartile range, and range. Balanced summaries will remain
distinct from pooled pixel descriptions. The completed synthetic-translation results do not supply
the missing upstream QA and resource measurements.


C.1    Resource-use analysis

Hyperspectral processing is computationally demanding because hundreds of co-registered bands
create high-dimensional data volumes, and useful analysis must also manage noise, calibration,
dimensionality, and algorithmic scaling (Plaza et al., 2009; Bioucas-Dias et al., 2013). SpectralBridge
adds correction models, multiple target products, tabular extraction, and QA records to that
baseline workload, making resource behavior part of the reproducibility evidence rather than a
purely operational detail.
Candidate source HDF5 files recorded for the study range from approximately 2.5–16 GB. Repository
guidance notes that some production workflows may require roughly 250 GB of RAM, but that value
is an operational planning estimate rather than a study result (Earth Lab, 2026t; Earth Lab, 2026ai).
On-disk HDF5 size is only one candidate predictor because compression, decoded dimensions, band
count, data type, processing mode, and concurrency can alter memory demand. Resource reporting
will therefore avoid a single unqualified memory requirement. For each run, the analysis will retain
source size in bytes; raster lines, samples, bands, and data type; available compression metadata;
complete-process-tree peak resident memory; wall time; worker count; backend; full- or half-flight
mode and window; completion status; and host CPU and RAM information.
Peak memory will be sampled for the parent process and descendants throughout each run, with the
sampling interval and aggregation rule recorded. The primary resource figure will plot peak resident
memory against both source file size and decoded cube size, identify failed or incomplete runs, and
distinguish worker count and full- versus half-flight processing. Associations will be stratified or
adjusted for these execution settings rather than pooled without qualification. Memory-aborted
runs will be reported as right-censored operational observations, not treated as completed peak-
memory measurements or silently excluded. The analysis will report rank associations with each
size measure; a regression will be added only if its form and residual behavior are defensible. This
describes operational scaling for the evaluated environment, not a hardware-independent complexity
guarantee.
For the updated bulk route, profile selected ENVI bytes and decoded dimensions, eligible observations,
requested pair-bands, window size, concurrent readers, storage characteristics, process-tree peak
RAM, and checkpoint/temporary/output bytes. Time cataloging, the statistics pass, aggregation,
the second error-evaluation pass, and compact report generation separately. Compatibility and
explicit dataset-materialization modes require their own measurements. A bounded representative
workload can establish resource use for that workload; a claim of superior performance requires a
stated comparator under matched conditions. The staged archive’s size does not establish a speedup
or measured peak-memory reduction (Earth Lab, 2026c; Earth Lab, 2026u).
